# ResQNet Security Enhancement Plan

## Overview
This document outlines the implementation plan to address the 5 residual security risks identified in the THREAT_MODEL.md:

1. No Certificate Authority / PKI
2. No rate limiting 
3. Shared master mesh key (AES-256-GCM)
4. ACK packets not signed
5. No key rotation

## Risk 1: No Certificate Authority / PKI

### Current State:
- Devices generate Ed25519 keypairs locally
- Signatures verified against raw public key embedded in signature envelope
- No central trust authority or certificate validation

### Required Implementation:
- X.509 Certificate Authority system
- Device enrollment with CSR submission
- Certificate signing and distribution
- Certificate Revocation List (CRL) management
- Chain of trust validation alongside Ed25519

### Files to Create/Modify:
- `backend/app/security/pki/` directory
  - `__init__.py`
  - `certificate_authority.py` - CA core functionality
  - `certificate_manager.py` - Certificate lifecycle management
  - `crl_manager.py` - Certificate revocation handling
  - `x509_validator.py` - X.509 certificate validation
- Update `crypto_utils.py` to include X.509 validation
- Update `packet_validation.py` to verify both Ed25519 and X.509 chain

### Implementation Details:
- CA generates its own Ed25519 keypair for signing certificates
- Devices generate keypair and submit CSR to CA during enrollment
- CA signs device public key with X.509 certificate (valid for 7 days)
- Relays and backend validate certificate chain + check CRL + verify Ed25519 signature
- CRL distributed via signed updates or backend endpoint

## Risk 2: No Rate Limiting

### Current State:
- Basic IP-based rate limiting middleware (120 requests/minute)
- Applied globally to all endpoints

### Required Implementation:
- Enhanced rate limiting with multiple strategies
- Per-endpoint rate limits
- Per-user/API-key rate limits
- Burst capacity and token bucket algorithm
- Different limits for ingestion vs administrative endpoints

### Files to Create/Modify:
- `backend/app/middleware/enhanced_rate_limit.py` - New enhanced middleware
- Update `main.py` to use enhanced rate limiting
- Configure different limits per endpoint group:
  - `/api/v1/incidents/ingest`: 60 req/min per IP (higher for emergency traffic)
  - `/api/v1/users/*`: 10 req/min per IP (administrative)
  - `/api/v1/incidents/ack`: 30 req/min per IP
  - WebSocket connections: 5 connections/min per IP

### Implementation Details:
- Token bucket algorithm for burst handling
- Redis-backed distributed rate limiting for multi-instance deployments
- Whitelisting for trusted gateways/internal services
- Metrics and monitoring integration

## Risk 3: Shared Master Mesh Key

### Current State:
- Single AES-256-GCM key shared across all nodes
- Key derived from environment variable or hardcoded default
- Compromise of one node = total system compromise

### Required Implementation:
- Replace shared key with per-session ECDH key exchange
- Ephemeral ECDH keys for perfect forward secrecy
- Key derivation function for session keys
- Secure key exchange protocol

### Files to Create/Modify:
- `backend/app/security/key_exchange/` directory
  - `__init__.py`
  - `ecdh_exchange.py` - ECDH key exchange implementation
  - `session_key_manager.py` - Session key lifecycle
  - `key_derivation.py` - HKDF or similar for key derivation
- Update `crypto_utils.py` to use session keys instead of master key
- Update mobile app to perform ECDH handshake before mesh communication
- Update packet structure to include ECDH public key for key exchange

### Implementation Details:
- Use X25519 curve for ECDH (compatible with Ed25519 infrastructure)
- Nodes exchange ephemeral X25519 public keys during mesh setup
- Derive session key using HKDF-SHA256 from shared secret
- Session keys rotated periodically or per communication session
- Perfect forward secrecy: compromise of long-term keys doesn't reveal past session keys

## Risk 4: ACK Packets Not Signed

### Current State:
- ACK packets generated by AcknowledgementService contain no cryptographic signature
- Vulnerable to spoofing/suppression attacks

### Required Implementation:
- Sign ACK packets with Ed25519 (same as emergency packets)
- Include signature in ACK response
- Verify ACK signatures on mesh nodes before accepting as valid
- Prevent ACK spoofing to suppress legitimate retransmissions

### Files to Create/Modify:
- `backend/app/services/acknowledgement.py` - Add signing to ACK generation
- `backend/app/security/crypto_utils.py` - Ensure signing functions available
- Update mesh networking logic in mobile app to verify ACK signatures
- Update packet schemas to include signature field in ACK responses

### Implementation Details:
- ACK packet structure: `{ "ackId": "...", "packetId": "...", "gatewayId": "...", "timestamp": "...", "signature": "ED25519:..." }`
- Signature computed over canonical ACK string (similar to packet canonicalization)
- Mesh nodes verify ACK signature before suppressing retransmissions
- ACK signatures use same Ed25519 keypair as device identity

## Risk 5: No Key Rotation

### Current State:
- Device Ed25519 keys generated once and never changed
- AES master key static unless environment variable changed
- No mechanism for graceful key migration

### Required Implementation:
- Automated key rotation schedules
- Key versioning and backward compatibility
- Secure key distribution mechanisms
- Graceful deprecation of old keys

### Files to Create/Modify:
- `backend/app/security/key_rotation/` directory
  - `__init__.py`
  - `key_rotation_scheduler.py` - Automated rotation timing
  - `key_version_manager.py` - Handle multiple key versions
  - `secure_key_distribution.py` - Securely distribute new keys
- Update `crypto_utils.py` to support key versioning
- Update mobile app key storage to handle key rotation
- Implement key rotation endpoints in API (admin only)

### Implementation Details:
- Ed25519 keys rotated every 30 days (configurable)
- AES session keys derived from ECDH - naturally ephemeral
- Master key (if any retained) rotated via secure distribution
- Key version included in signatures/encryption headers
- Backward compatibility: accept N previous key versions during rotation window
- Secure key delivery: encrypted with receiver's current public key

## Implementation Priority Order:
1. **Risk 4: ACK Packets Not Signed** - Simplest, highest impact for mesh security
2. **Risk 5: No Key Rotation** - Builds on existing crypto infrastructure
3. **Risk 2: Rate Limiting** - Enhances existing middleware
4. **Risk 3: Shared Master Mesh Key** - Requires protocol changes
5. **Risk 1: No CA/PKI** - Most complex, foundational trust system

## Estimated Effort:
- Risk 4: 2-3 days
- Risk 5: 3-4 days  
- Risk 2: 2-3 days
- Risk 3: 4-5 days
- Risk 1: 5-7 days
- Total: ~2-3 weeks for complete implementation

## Testing Strategy:
- Unit tests for each new component
- Integration tests for security workflows
- Penetration test validation (extend existing test suite)
- Interoperability testing between versions
- Performance impact assessment

## Rollback Plan:
Each enhancement designed to be backwards compatible where possible:
- ACK signing: unsigned ACKs still processed (warning logged)
- Key rotation: multiple key versions supported
- Rate limiting: existing middleware preserved as fallback
- ECDH: fallback to master key if exchange fails (degraded security)
- PKI: X.509 validation optional, falls back to raw key validation

## Dependencies:
- Add `cryptography` package to requirements if not already present (likely is)
- Consider `redis` for distributed rate locking in multi-instance deployments
- No major architectural changes required

## Success Criteria:
- All penetration tests pass with enhanced security
- No degradation in packet processing latency (<50ms)
- Successful key rotation without service disruption
- ACK spoofing attacks prevented in test scenarios
- Certificate enrollment and revocation functional
- Rate limiting effective under load testing
